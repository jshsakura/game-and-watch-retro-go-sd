# SNES 60 FPS 후보: 실기 전 하네스 검증 정리

2026-10-01. `perf/snes-60fps-span`에서 대기 루프 구간 계산 후보를 **9개 게임·12개 조건**으로
검증했다. 완료 실행은 **26회·30,000 guest frames**다. 별도로 파판 5의 1200프레임 A 실행
1회가 시간 제한에 걸렸고 실패 기록도 보존했다. 32X 작업 중인 실기는 사용하지 않았다.
**60 drawn FPS 달성 여부는 아직 미측정**이다.

## 비교 대상과 방법

- 워크트리: `/home/pi/app/jupyterLab/notebooks/game-and-watch-retro-go-sd-snes60`
- 상위 기준: `dbc36be1`; 코어 후보: `e33537c06618e88786f518221787a1e033ba303b`
- A: 기존 bake / `SNES_BAKE_BULK=0`; B: 같은 소스에 `SNES_BAKE_BULK=1`만 추가.
- shipping 기본값은 계속 **0**. 구현 설명은 [첫 실험](SNES_60FPS_SPAN_EXPERIMENT.md)에 있다.
- 실제 기기와 같은 Thumb-2 65816 / SPC700, 기존 PPU 최적화, ASM ROMCACHE OFF.
- Arm GNU 15.2.Rel1, `-O2`, Cortex-M7 hard-float; QEMU 10.0.13 / `mps2-an500` / icount.
- 콜드 부팅, 워밍업 0, 입력 없음이 기본. 200프레임 창과 프레임별 명령 수를 보존했다.
- 조건당 A 1회 / B 1회. 젤다 기본 조건과 마리오 월드에 A-after를 1회씩 추가했다.
- 코어 profiler OFF. PCM 파일 출력·해시·최종 상태 직렬화는 계측 구간 밖이다.
  프레임 추적 하네스의 비교이며 이전 하네스의 절대 명령 수와 분모를 섞지 않는다.
- 총비용은 EMU + PCM top-up. `zelda-video`에만 화면 버퍼 memcpy 비용을 더했다.

계측값은 **명령 수**다. 하네스의 가상 FPS 환산 표기를 제거했다.
캐시·메모리 대기·실제 LCD 전송·오디오 DMA ISR은 QEMU에서 재현되지 않는다.
전체 firmware 빌드는 아니다. 정확한 define 목록은 manifest에 있으며 firmware의
`SNES_PPU_DIRECT_MATH` 등 화면 합성 설정은 이번 rig에 포함하지 않았다.

화면 버퍼 조건은 직접 렌더링과 320×240 memcpy를 검증하며 실제 LCD 전송은 포함하지 않는다.

## 정확성과 음원

12개 A/B 비교가 다음 항목을 모두 통과했다.

1. **각 프레임** framebuffer·raw audio 해시 일치: 총 **13,800쌍**.
2. 최종 `snes_saveload` 실제 저장 스트림의 길이·64-bit hash 일치.
   CPU / SPC / DSP / DMA / PPU / 카트 / WRAM을 포함한다.
3. 전체 raw PCM의 **SHA-256과 바이트 수** 일치: 1200프레임 638,400 bytes,
   600프레임 319,200 bytes. ROM·ELF도 실행 전후 해시가 같다.
4. 원본 소스와의 **109,886 span 차등 검증 + ASan/UBSan** 근거를 유지했다.
   해당 검증 후 코어 후보는 바뀌지 않았다.
5. 비교 도구에서 상태·중간 음원 불일치, 프레임 누락, 다른 ROM, 미완료 실행을
   실패시키는 회귀 검사 **6개**도 통과했다.

파판 5의 1200프레임 A는 28초 제한으로 종료돼 **완료 판정에서 제외**했다.
자동 재시도나 잘린 창의 성능 집계는 하지 않았다. 별도 600프레임 A/B는 통과했지만
그 구간의 PCM은 모두 0이므로 **활성 음원 검증 사례로 세지 않는다**.
다른 게임·젤다 조건에는 nonzero PCM이 있었고 peak·RMS·샘플 수도 기록했다.

실제 `snes_audio_stretch.c`를 연결한 기존 연속성·pitch 검사는 **0 failures**였다.
젤다·마리오 월드의 실제 PCM을 shipping follow 모드로 처리한 A/B WAV는 고정
60 / 61 / 52.65 **emulated frames/sec** 시뮬레이션 6조건 모두 SHA-256이 같고 underruns 0이었다.
고정 공급 스케줄은 실기 draw/skip이나 IRQ 지터 재현이 아니다. 52.65 emulated 입력은
과거 **52.65 drawn FPS 장면의 재현을 뜻하지 않는다**. 실기 청취 판정도 하지 않았다.
PCM/WAV는 로컬 build 디렉터리에만 보존했다.

## 빌드 크기와 산출물

`spin_bake_run_span` object text는 **328 → 412 bytes (+84)**다.
기본 하네스 ELF text는 **202,956 → 203,020 bytes (+64)**, data·BSS는 같다.
화면 버퍼/600프레임 ELF도 text +64이며 data·BSS 변화가 없다.
실기 firmware link와 overlay·ITCM 여유는 아직 확인하지 않았다.

[증거 manifest](../tools/snes_bulk_wait/results/20261001-harness-ready/manifest.json)에
ROM·ELF·소스·container ID, 실제 argv·옵션, 완료/실패 기록과 요약을 묶었다.
같은 디렉터리에 원본 로그 gzip, **ROM을 포함하지 않는 ELF 6개**의 gzip,
소스 patch와 빌드 로그도 보존했다. gzip에서 원본 바이트와 해시를 복원할 수 있다.
실행 중 상태를 조회하지 않았고 각 유한 프로세스의 종료 후에만 결과를 읽었다.

로컬 원본은 `build/snes-harness-ready/`에 있다. ROM은 외부 입력을 읽기만 했으며
산출물에 복제하지 않았다. 기존 실행을 덮어쓰지 않는 경로를 사용했다.

```sh
python3 tests/test_snes_bulk_evidence.py
python3 tools/snes_bulk_wait/compare.py A/output.log B/output.log
python3 tools/snes_bulk_wait/build_rig.py --out build/NEW_ARM --bulk
```

`build_rig.py`는 빌드만, `run_case.py`는 명시한 입력·case를 실행하고,
`pack_evidence.py`는 완료/실패 기록을 묶기만 한다. 각각 `--help`에 인자가 있다.
기존 case는 재사용하고 의도적인 A-after에는 `rerun_reason`을 남겼다.

## 32X 종료 후 실기 확인 순서

기기는 사용자의 32X 작업에 할당되어 있다. 종료 통보 전까지 flash·reset·SD 배포를 하지 않는다.

1. 기존 **젤다 52.65 drawn FPS 저장 장면**의 실제 ROM·save hash와 설정을 확보한다.
   이번 콜드 부팅/입력 구간이 그 저장 장면과 같다고 가정하지 않는다.
2. bulk OFF/ON만 다른 전체 firmware와 SD core 묶음을 만들고 firmware link,
   overlay·ITCM 여유, ELF/intflash/core 조합의 신원을 확인한다.
3. 검증된 완료 이벤트 경로로 같은 장면·클록·화면 배율·16kHz 음원·profiler OFF의
   **A→B→A**를 수행한다. 기존 `drawn_ab.sh`/`bench.sh`의 SWD 폴링은 사용하지 않는다.
4. 젤다를 먼저 확인하고 효과가 큰 **마리오 월드 → 드래곤즈 매직**을 비교한다.
   저장 장면을 고정하고 drawn/emulated FPS, 지연 분포, underrun, 화면·소리를 남긴다.

과거 bake 실기의 마리오 월드 33.27 drawn FPS, 드래곤즈 매직 34.17 drawn FPS는
[기존 기록](SNES_WAIT_LOOP_BAKE.md)의 다른 측정 구간이다. 이번 명령 수 감소를 그 FPS에
직접 곱하지 않는다. 젤다는 무거운 프레임 개선이 없어 **이 후보만으로 60 FPS를 달성한다고
볼 근거가 없다**. 다음 검수 후보는 CPU/scheduler 진입·복귀와 gap-free 음원의 사용되지
않는 주기 탐색 비용이다.
