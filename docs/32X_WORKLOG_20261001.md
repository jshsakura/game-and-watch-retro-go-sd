# 32X 작업 이력 (2026-10-01)

이슈: #48. 브랜치: `perf/32x-hle-itcm` (picodrive 서브모듈 `gnw/32x-hle` 471181d8).

## 결과

After Burner(32X), 콜드부팅, 0~119 프레임 START 6on/6off, warmup 540, window 180, 340 MHz, fullscreen 0,
tear_guard 0. 모든 측정에서 끝 화면(827a6a42)과 끝 오디오(13087d2b) 해시가 기준과 같았다.

| 단계 | 실기 fps | 판정 |
|---|---:|---|
| 원래 인터프리터 | 10.11 | 기존 기록 (job-jmdc2ory) |
| 기존 네이티브 후보 | 11.58 ~ 11.69 | 기존 기록 |
| SH2 HLE (믹서, blit B, 유휴 회전, 열 채우기) | 13.59 | 유효 triplet, 기존 후보 대비 +16.4% |
| HLE 네이티브 군살 제거 | 13.98 | 유효 triplet, +0.56% |
| 68K 메인 루프와 SH2 동기화 경로를 ITCM으로 | 17.29 / 17.38 | triplet 두 번 모두 무효 (아래 참고) |
| 같은 두 빌드, XIP 8KB 정렬 할당기로 | **17.21** | 유효 triplet, A 14.49/14.46, 드리프트 −0.20%, **+18.9%** |

마지막 단계는 기준 A가 실행마다 13.95와 14.39 두 값을 오가서 앞뒤 드리프트가 2.8%, 3.1%로 사전 한계(0.5%)를
넘었다. B는 두 번 다 17.3fps로 0.5% 이내에서 같았고, 이득(+20~25%)이 흔들림보다 훨씬 크다. 한계를 완화하지
않고 무효로 기록한다.

## 기준 A가 두 값을 오간 이유: XIP 페이로드의 캐시 위상

A는 실행마다 12,510ms 아니면 12,900ms였고, 빠른 쪽은 워밍업까지 1초 빨랐다. 부팅 때 정해지는 상태다.
매 실행에서 `g_xip_addr`를 읽어 보니(A, B, A, A, B, A) 둘로 정확히 갈렸다.

| XIP 주소 mod 8KB | A fps |
|---|---|
| 0x0000 (0x9294c000, 0x92d70000) | 14.452, 14.459 |
| 0x1000 (0x92cb9000, 0x92edd000) | 13.946, 13.979 |

8KB는 이 칩의 I-cache 한 way다(16KB, 2-way, 32B 줄). 할당기는 4KB 지우기 단위로만 맞추므로 32x.xip의 위상은
앞에 캐시된 파일이 정했다. 같은 빌드가 사용자 기기에서도 부팅 운에 따라 3% 느릴 수 있었다는 뜻이다.

수정: `gw_flash_alloc.c`가 재배치되는 XIP 블롭(`relocate_cb` 있음)을 8KB 경계에 놓고, 링 base도 8KB에 맞춘다.
일반 파일은 그대로 4KB로 채운다. `tests/test_flash_alloc_xip_align.c`가 실제 할당기를 컴파일해 확인하고,
고치기 전 할당기(cd893451)로는 실패한다. 내부 플래시 여유가 276B뿐이라 수정은 24B 안에 넣었다(여유 260B).
base가 4KB 홀수 위치였던 기기는 메타데이터 base가 달라져 ROM 캐시가 한 번 초기화된다.

정렬 후 A 다섯 값은 14.465~14.578(0.8%), B 세 값은 17.213~17.231(0.1%). 첫 triplet은 드리프트 0.501%,
둘째 묶음의 앞 triplet은 −0.58%로 무효였고, 뒤 triplet이 유효했다. B는 정렬 위상에서 17.22로, 어긋난 위상의
17.25~17.38보다 조금 느리다. 어느 위상이 빠른지는 링크 배치마다 다르다. 이 수정이 주는 것은 "한 빌드는 한 속도"다.

## 방향: 같은 결과를 내면서 덜 에뮬레이트한다

트레이스로 본 After Burner의 SH2 일은 세 루틴이 81%였다. 슬레이브의 소프트웨어 PCM 믹서 39%, 마스터의
스프라이트 확대 blit 26%, 마스터 대기 루프 16%(이미 접혀 있었음). 조각 단위로 쪼개 접던 기존 방식 대신
루틴 단위로 통째로 네이티브로 처리했다. 모두 명령 패턴으로 인식하며 게임 이름, 고정 PC, ROM 해시를 쓰지 않는다.

- `mix_native`: 출력 샘플 하나를 한 번에 만든다. 보이스는 "icount > 0이면 실행" 규칙으로 통째로 접는다.
- `blitb_native` (+ `GNW_BLIT_AC`일 때 `blitc_native`, `blita_native`): 스프라이트 한 줄을 한 번에 처리한다.
- `idle_native`: 슬레이브의 링 대기 회전을 인터프리터와 같은 차감 순서로 접는다.
- `fill_native`: 펼쳐진 열 채우기를 요소 단위로 접는다.

각 네이티브는 인터프리터와 2,048회 대조(6,016바이트 전체 컨텍스트와 건드린 메모리)를 통과했다.

## 실기가 가리킨 진짜 병목

rig(QEMU 명령 수) 감소가 실기 이득을 예측하지 못하게 됐다(rig −2.7%, 실기 +0.56%). 실기에서 직접 쟀다.

- light profile(lean HLE, 14.09fps): m68k 구간 38.2%, 마스터 SH2 22.9%, 슬레이브 SH2 17.3%, FM 5.3%,
  Z80 2.8%, 합성 2.6%, MD VDP 2.6%.
- PC 샘플링(SysTick 1kHz, 256B 블록): XIP 41% 이상, ITCM 29%, RAM 4.5%. `m68k_run` 한 블록이 8.5%였다.
  68K는 프레임당 수천 명령뿐인데 명령마다 외부 플래시 캐시 라인을 다시 채우고 있었다.

그래서 `m68k_run`과 32x.c의 동기화·이벤트·IRQ 경로(2.7KB)를 `.overlay_md32x_itc` 끝에 붙였다. 코드는 그대로이고
주소만 바뀐다. 공간은 MD 스프라이트 라인 표 `HighLnSpr`(7,680B)를 RAM_EMU로 옮겨 만들었다.

## 함정 (다시 밟지 말 것)

- `muls.w`는 인터프리터에서 1사이클이다. `dmuls.l`만 2사이클이다.
- `no_polling`은 dt를 지난 호출에서만 세운다. 버스 읽기 안의 poll 감지는 "실행 후 차감" 순서의 icount를 본다.
- 호출처가 하나뿐인 큰 static 네이티브를 GCC가 인터프리터 루프에 인라인하면 레지스터 압박으로 +20%가 난다.
  `noinline`이 필수다.
- 인식 실패 경로는 싸야 한다. 주소 계산 실수로 매번 거절되던 blit B가 swap.b마다 86바이트 비교를 8번 돌아
  프레임당 330만 명령을 더 썼다.
- 훅 한 줄을 `#ifdef`로 가를 때 줄 뒷부분이 `#endif` 줄로 밀려 버려질 수 있다. Doom 게이트가 잡았다.
- 68K VDP 재기록 대기 루프 접기는 rig −3.8%였지만 오디오 해시가 바뀌었다. 재운 68K가 인터럽트 시점보다 늦게
  깨어나기 때문으로 보인다. 되돌렸다.
