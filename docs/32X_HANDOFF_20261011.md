# 32X 성능 핸드오프 (2026-10-11)

다음 세션은 이 문서부터 읽습니다. `32X_CLOSED.md`는 "성능 작업 종료"라고 적혀 있지만, 아래 스택이 병합되어 그 결론이 바뀌었습니다. 이 문서가 최신입니다.

## 결과

기기 실측(340 MHz, 600 emu 프레임, 워밍업 900, A/B/A, 화면 해시 일치, 스크린샷 확인)입니다. 게임당 1회 측정이고, 모두 attract/타이틀 장면이지 실제 플레이가 아닙니다.

| 게임 | 기준선 fps | 패치 fps | 이득 |
|---|---|---|---|
| Virtua Fighter | 10.852 | 17.770 | +63.8% |
| Chaotix | 15.785 | 20.569 | +30.3% |
| Kolibri | 14.713 | 19.027 | +29.3% |
| Doom | 30.709 | 34.616 | +12.7% |
| After Burner | 22.627 | 24.006 | +6.1% |

기준선은 `testbed-full-20261005-pcm-r2` 펌웨어입니다. 기기 오디오 해시는 항상 0이라 소리는 기기에서 검증하지 못했고, rig 오디오 해시(Chaotix 한 게임)만 같음을 확인했습니다.

## 병합된 것

- PR #56: 첫 병합. **picodrive 패치가 적용되지 않는 상태였습니다.** 아래 교훈 참고.
- PR #58: `patches/picodrive-32x-sh2-loop.patch`를 picodrive `10a5d460` 위로 다시 만들었습니다. SH-2 루프 뼈대(지연 슬롯/IRQ 한도 꼬리, 16-way `adr`+`ldr.w pc` 점프 테이블, 훅을 op 함수 안으로 이동), 가변 fetch 창(q1), Z80 중복 SZ_BIT 테이블 제거(S03)를 포함합니다. 링커 스크립트는 Z80 테이블을 ITC bss에서 DTCM으로 옮기고, DTCM 예약을 23K+64 B로, 시작을 256 B 낮췄습니다(스택 보호 MPU 영역과 겹쳐 Memfault가 났던 문제의 수정).
- PR #59: `Makefile.common`의 `ApplyPatches`가 `patches/apply.sh`를 빌드마다 실행합니다. picodrive 패치는 적용도 안 되고 이미 적용된 것도 아니면 빌드가 실패합니다. `tests/test_apply_patches_wired.sh`가 연결을 고정합니다.

## 교훈 (비싸게 배운 것)

1. **패치가 실제 빌드에 들어갔는지 먼저 증명합니다.** #56은 `5cc10e1a` 기준으로 만든 패치를 `10a5d460`을 가리키는 저장소에 넣었고, `apply.sh`가 "skip (applied/conflict)"만 찍고 넘어가서 링크도 컴파일도 통과했습니다. 증명은 `md32x__gnw_sh2_fastloops` 주소를 패치 있는 ELF와 없는 ELF에서 비교하는 것이었습니다. U 빌드(패치 없음) 이득은 0이었고, V 빌드(패치 있음)는 위 표입니다.
2. **rig 숫자는 이득의 근거가 아닙니다.** rig 호스트 명령 수는 기기에서 여러 번 부호가 뒤집혔습니다. rig는 화면·오디오 해시 일치 확인에만 씁니다. 이득은 기기 A/B/A로만 인정합니다.
3. **빌드 경로마다 검사가 다릅니다.** 기기용 arm 빌드는 링커 ASSERT(DTCM 예약, 내장 플래시 여유 256 B)를 통과했는데 정식 `make release`는 둘 다 실패했습니다. 병합 전에 정식 릴리스 빌드 한 번이 필요합니다.
4. **기기 에이전트는 모니터를 기다리다 멈춥니다.** 끝난 빌드를 30분 기다린 적이 있습니다. 파일과 프로세스 상태로 확인하고, 알림 없이 도는 백그라운드 일을 두지 않게 지시합니다.
5. **기기는 idle 전원 끄기로 꺼집니다.** 대기 상태에서는 SWD로 못 깨우고 물리 버튼만 됩니다. 세션 시작 직후 `main_menu_timeout_s`를 RAM에서 0으로 만듭니다(`memory/device-remote-only.md`).

## 시도하고 버린 것 (다시 하지 않습니다)

- 렌더 지연(n1, `gnw_md_defer`)은 After Burner에서 검은 마지막 프레임과 화면 해시 불일치를 냈습니다. 전체 스택으로 Doom +26%였지만 병합하지 않았습니다. 이득은 크니 두 LCD 버퍼 경로(`PicoDrawSetOutBuf32X`)를 고쳐서 되살릴 가치가 있습니다.
- DIVU 하드웨어 경로(0.05%), DIV1 체인 접기(Doom 2.7% 이하), `__builtin_unreachable` switch 힌트, 루프 안 인라인 SDRAM 쓰기, `p32x_sh2_write*`의 직접 SDRAM/DA 쓰기, YM2612 무음 채널 빠른 경로(오디오 해시 변경), chan_render의 `restrict`, q2(S4와 충돌), `tbh` 점프 테이블(UsageFault), Z80을 XIP로 보내기(기록상 +2.8~3.5% 손해), MPU 변형 B(+0.21%)와 C(링크 실패).

## 아직 안 한 것

1. **정식 릴리스 빌드로 기기 확인.** 현재 `testbed`에서 `make release`로 만든 빌드를 설치(모든 코어 같은 GIT_TAG, 설치 도구는 `tools/32x_devtools`)하고 위 5개 게임을 다시 잽니다.
2. **렌더 지연 되살리기.** 위 항목 참고. 메뉴 복귀 시 `md32x_repaint`도 확인해야 합니다.
3. **미검증 항목.** 메뉴 복귀, 부팅 카운터 DR28, Doom/Chaotix 힙 최대치(DTCM 23K 예약 아래), 다른 32X 게임들, 실제 플레이(attract 아님), 기기 소리.
4. **문서 정리.** `32X_CLOSED.md`와 `32X_FAILED_APPROACHES.md`에 이번 결과를 반영합니다.
5. **CI.** 이 브랜치들에는 체크가 보고되지 않았습니다. `package.yml`이 `ApplyPatches`를 타는지 한 번 확인합니다.

## 알아 둘 것

- `apply.sh`의 gwenesis 패치 두 개는 지금 적용도 되돌리기도 안 되어 항상 skip으로 나옵니다. 건드리지 않았습니다.
- `external/picodrive`와 `external/gwenesis`는 패치가 일부러 dirty로 만들기 때문에 dirty 검사에서 제외했습니다.
- 증거는 `build/32x-device-20261010-mpu/`의 `jobs-V-{ab,chaotix,doom,vf,kolibri}-r1/`, `restore4/`에 있습니다. 이 폴더는 추적되지 않습니다.
- 작업은 항상 브랜치에서 하고 PR로 병합합니다(`memory/work-via-branch-pr-merge.md`).
