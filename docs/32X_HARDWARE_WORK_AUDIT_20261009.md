# 32X 하드웨어 공통 연산 제거 검토 — 2026-10-09

검토 기준은 S01/S03/S04를 합친 완료 정상 소스와 GCC 15 ELF다.
기존 PCM-r2 대비 실기 Doom 1 triplet +2.13887%와 ITCM 여유 1,280 B는
이미 완료한 결과이며, 아래 새 후보의 성능으로 인용하지 않는다.
이번에는 소스와 완료 기계 코드만 읽었다. 새 구현·빌드·rig·기기 실행은 없다.

동일하게 빨라진다는 뜻은 아니다.

## S07: 같은 원본 줄의 합성 결과 재사용

현재 packed-pixel 루프는 매 행 `dram[line]`에서 원본 주소를 얻고
`gnw_line_pp`를 호출한다. 원본 주소가 앞선 행과 같은지는 검사하지 않는다.

첫 검토 범위는 **H40 packed 모드, scan callback 없는 하나의 동기식 그리기 호출**이다.
같은 원본 주소·shift·bank·palette가 유지되고, 앞 행과 현재 행의 MD index가 모두
배경색이라면 32X가 전체 행을 덮으므로 앞서 만든 640 B 출력 줄을 복사할 수 있다는
가설이다. 출력 stride와 원본/목적지 비중첩도 확인해야 한다. MD가 비배경인 행은
같은 index만으로 같은 RGB라고 판단하면 안 된다. raster palette 효과가 있을 수 있다.

이 조건에서는 별도 영구 행 캐시 없이 같은 호출의 이전 출력과 작은 지역 상태만
사용할 수 있다. 호출 경계를 넘거나 callback이 개입하는 경우에는 재사용하지 않는다.
H14의 MD nametable cache, H16의 전체 MD 프레임 생략과 구별되는 전제다.
그림 자체의 쓰기는 남고 palette 조회·합성 판단을 줄이는 방식이다.

**미확인:** 같은 원본 주소가 실제로 얼마나 반복되는지, MD 배경 검사와 640 B 복사
비용을 빼고 이득이 남는지. 화면이 비슷해 보이는 것만으로 원본 줄이 같다고 보지 않는다.
먼저 총 행/동일 원본 행/조건 충족 행/이미 solid-run으로 싼 행을 구분해 집계한다.
재사용 가능 행이 드물면 후보를 닫고 행 캐시 변형을 연속 시험하지 않는다.

과거 stationary Doom light profile에서 32X 합성은 5.65868%였다. 이는 당시 해당
구간 전체 비용이며 S07의 절감률도, 현재 결합 후보의 비용 비중도 아니다.

## S06: DMA 블록 내부의 반복 쓰기 경로 선택 제거

이미 `dmac_memcpy`가 있으므로 DMA 최적화 자체를 새 발견으로 세지 않는다.
남은 부분은 source를 직접 읽은 뒤에도 word마다 `p32x_sh2_write32` 경로를 거치는 점이다.
완료 GCC15 ELF의 `0x2404ee7a..0x2404ee94`에 write-map 조회, ROR16,
간접 호출 BLX가 실제 남아 있다.

후보는 DMA 진입에서 실제 source/destination map과 전체 길이를 한 번 확인하고,
안전한 연속 일반 메모리 구간에서 직접 복사하는 것이다. 일반 SH2 dispatch나
매 guest load에 hook을 추가한 H04/G03/G07과는 진입 비용을 내는 위치가 다르다.

처음에는 MMIO·palette·PWM/FIFO·overwrite DRAM·ROM 쓰기·영역 경계 통과와
물리 alias/중첩을 제외한다. DRAM byte write는 일반 주소에서도 0 byte를 건너뛰므로
단순 memcpy로 바꾸면 안 된다. 정렬·byteswapped 저장 형식·전송 단위·최종
SAR/DAR/TCR·DMA 완료 IRQ를 보존해야 한다. DRC/무효화/진단 부작용이 있는 경로도
빠른 경로로 우회하지 않는다. 중첩 복사는 기존 순차 쓰기 결과를 기준으로 삼는다.

**미확인:** 현재 작업량에서 이 조건에 드는 DMA byte 수와 호출 수.
과거 PC 표본에서 함수가 보이지 않는다는 것만으로 호출 0회라 판단하지 않는다.
유효 전송량이 적으면 구현하지 않는다.

## S05: VDP autofill의 wrap 계산을 두 구간으로 분리

현재 하드웨어 fill 구현은 같은 16-bit 값을 쓰면서 매 word마다
`a = (a & 0xff00) | ((a + 1) & 0xff)`를 수행한다.
GCC15에서도 `0x2404f0e0..0x2404f0fc` 반복에 AND/UXTB/ORR 등이 남아 있다.

정상 register 길이 1..256 word에서는 256-word 경계 앞/뒤의 최대 두 연속 구간으로
나누면 주소 wrap 계산을 루프 밖으로 뺄 수 있다. 최종 fill address/data register,
선택 DRAM bank, `len > 8` busy 조건과 `3 + len` 완료 이벤트는 그대로 보존한다.
임의 16-bit 값을 byte memset으로 채우면 안 된다. 저장 상태에서 비정상 길이가
들어올 가능성도 확인하고 빠른 경로 범위 밖에서는 기존 처리를 유지한다.

과거 PC sampling에서 `p32x_vdp_write16` 전체는 0.42%/0.61%였다.
현재 fill 전용 지분은 아니며 적은 표본이다. 이 후보를 큰 개선으로 소개할 근거가 없다.

## 완료 자료로 제외한 항목

- **U02 빈 scheduler 묶기:** 초기 실패 뒤 완료된 run-000003을 찾았다.
  3개 workload의 948,217 measurement steps에서 제거 가능 subdivision은 0회였다.
  실패 목록을 이 후속 결과로 수정했다.
- **G05 PWM 동일 좌우 변환 공유:** 전체 절감이 이미 0.0016~0.0091%로 측정됐다.
- **H08 PWM 대기 park:** 음원 손상 및 정확한 wake 후 이득 소실 이력을 재사용한다.
- **L8/LTDC 전환:** 기존 census는 32X 색 index 256/256 사용, MD 비배경 행 80..223,
  양방향 pixel priority 문제를 확인했다. 동일 구조를 다시 새 후보로 올리지 않는다.

다음 진단을 진행한다면 고정된 창 하나당 S07 유효 반복 행, S06 유효 DMA byte,
S05 fill 호출/길이를 함께 집계하는 편이 낫다. 부팅과 측정 창을 나눠 보고,
진단 수치를 clean 성능으로 인용하지 않는다. 이번 검토에서 진단은 시작하지 않았다.
