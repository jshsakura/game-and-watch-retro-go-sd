# 🧠 선배들의 묘수 분석 및 실기(Hardware) 돌파를 위한 초극한의 최적화 전략

> **목적**: QEMU 하네스 환경의 부정확한 가상 클럭/캐시 시뮬레이션에 속지 않고, **실제 STM32H750/B0 실기 보드(Game & Watch)**의 버스 매트릭스 대역폭 및 플래시/램 대기 사이클을 뚫어내어 **'천지를 먹다 2'의 실기 60fps 구동**을 달성하기 위한 물리 레벨의 최적화 설계를 명세한다.

---

## 1. 선배들의 "성공한 묘수" (기축적된 무기)

### 🚀 묘수 A: 오디오 하위 에뮬레이션 제거 ➔ Native HLE Mixer 대체
* **레슨**: GBA M4A 믹서 HLE 및 SNES APU HLE는 무거운 가상 칩 에뮬레이션을 걷어내고 MCU 네이티브 재생기로 대체하여 프레임 부하를 **최대 60%** 절약했습니다.
* **CPS-1 대입**: Z80 코어와 YM2151 에뮬레이터 에뮬레이션을 제거하고, QSound/YM2151 음악 시퀀스 데이터를 **M7 네이티브 C 코드로 HLE 재생**하여 오디오 버하를 3% 이하로 축소합니다.

### 🚀 묘수 B: MPU 설정을 통한 쓰기 지연 방지 (1.4 ~ 2.1 ms 세이브)
* **레슨**: 프레임 버퍼 MPU 영역을 `Normal Non-cacheable`로 설정하여 비디오 전송 시 CPU 쓰기 버퍼 대기 지연을 해소했습니다.
* **CPS-1 대입**: LCD 출력 버퍼의 전송 영역을 MPU 수준에서 캐시 비활성화 처리하여 전송 지연을 최소화합니다.

## 2. 하네스 전용에서 탈피하기 위한 "실기 돌파용 5대 하드웨어 치트키"

실기 보드에서 병목이 생기는 진짜 원인은 CPU 성능 분배뿐만 아니라 **버스 충돌(Bus Contention), 캐시 미스 오버헤드, 느린 외장 장치(SD카드) 읽기**에 있습니다. 이를 극적으로 우회할 하드웨어 제어 트릭입니다.

### 💡 [치트 1] 물리 램 분할 배정을 통한 Bus Contention (버스 충돌) 차단
* **원인**: STM32H7의 Multi-AHB 버스 매트릭스 상에서 CPU가 그래픽 캐시를 읽는 동안, 동시에 LCD 컨트롤러(LTDC)나 DMA2D가 동일한 RAM 영역의 프레임 버퍼를 스캔하면 하드웨어 버스 중재(Bus Arbitration) 지연이 발생해 CPU가 매 사이클 수십 클럭씩 멈춰 서게(Stall) 됩니다.
* **해법**: 프레임 버퍼와 스프라이트 타일 캐시를 **물리적으로 분리된 하드웨어 RAM 뱅크**에 강제 적재하여 버스 충돌을 제로로 만듭니다.
  * **AXI SRAM (SRAM1/2, 384KB)**: LTDC 프레임 버퍼 전 전용 배정.
  * **AHB SRAM (SRAM3, 64KB)**: 256KB 스프라이트 타일 캐시 중 일부 혹은 에뮬레이터 힙/오디오 버퍼 배정.
  * **DTCM (64KB - D1 Domain)**: CPU 전용 로컬 램으로, 68000 WRAM(64KB)을 여기에 올려 LCD 전송 버스가 흔들려도 CPU 연산은 전혀 방해받지 않도록 격리.

### 💡 [치트 2] "No-SD-Read during Gameplay" (플레이 중 SD 카드 접근 원천 금지)
* **원인**: 게임 도중 오디오 효과음이나 스프라이트 타일을 읽기 위해 SD 카드를 수시로 찌르는 것은 DMA를 쓰더라도 SDIO 버스 속도 한계(25~50MHz) 및 FATFS 파일 시스템 레이어로 인해 실기에서 무조건적인 끊김 현상(Stuttering)을 유발합니다.
* **해법**: 플레이어 구동 도중에는 SD 카드에 단 1바이트도 읽기 요청을 보내지 않습니다.
  * **전술**: 스테이지 시작(로딩 화면) 시점에, 해당 스테이지에 사용되는 모든 사운드 샘플(OKIM6295 ADPCM) 및 CHR 스프라이트 타일셋을 **External QSPI Flash의 비어있는 빈 캐시 영역으로 통째로 고속 덤프**해둡니다.
  * 플레이 중에는 SD 카드가 아닌, 104MHz 듀얼/옥타 속도로 작동하는 **QSPI Flash 영역에서만 직접 런타임 스트리밍 및 캐싱**을 수행합니다.

### 💡 [치트 3] L1 D-Cache 무효화(Invalidation) 오버헤드 극소화
* **원인**: DMA2D나 MDMA가 플래시에서 타일을 램 캐시로 복사한 후, CPU가 변경된 데이터를 인지하도록 캐시를 지우는 `SCB_InvalidateDCache()`를 무턱대고 전체 대상으로 호출하면 수천 사이클의 CPU Stall이 납니다.
* **해법**: 
  * 캐시 영역 전체를 날리지 말고 `SCB_InvalidateDCache_by_Addr(cache_addr, size)`를 사용해 미스가 발생한 타일 영역(예: 8x8 타일 = 64바이트)만큼만 주소 단위로 정밀 무효화합니다.
  * 또는 스프라이트 캐시가 있는 SRAM 영역의 MPU 속성을 **Write-Through**로 튜닝해 오버헤드를 0으로 만듭니다.

### 💡 [치트 4] 비정렬 메모리 접근 (Unaligned Memory Access) 강제 제거
* **원인**: 68000은 빅 엔디언(Big Endian)이며 홀수 번지에서도 16/32비트 메모리 읽기/쓰기를 지원하지만, Cortex-M7이 이를 하드웨어 수준에서 처리할 때 버스 사이클이 2배로 늘어나는 패널티가 붙습니다.
* **해법**: 빌드 타임에 정적 재컴파일러(Static Recompiler)가 C 코드로 주소 연산을 변환할 때, 홀수 번지 데이터를 강제로 **32비트 정렬(4바이트 Align) 구조로 재정렬**하고 메모리 읽기를 32비트 단일 클럭 정렬 연산으로 완전히 치환합니다.

### 💡 [치트 5] 가상 PC 번지 24비트 비트마스크 연산의 하드웨어 우회 (MPU 활용)
* **원인**: 68000의 24비트 주소 지정을 흉내 내기 위해 매 명령어마다 `addr & 0xFFFFFF` 마스킹을 수행하면 `ubfx` 등의 어셈블리가 낭비됩니다.
* **해법**: 마스킹 연산을 날리고, M7의 **MPU(Memory Protection Unit)** 영역 설정을 조작하여 `0x00000000 ~ 0x00FFFFFF` 주소를 OSPI Flash 매핑 영역(`0x90000000`)으로 가상 포인팅시킵니다. CPU가 마스크 연산 없이 주소를 던져도 하드웨어가 알아서 플래시 주소로 찾아가게 만듭니다.

## 3. 💥 1클럭, 1바이트도 짜내는 "우주 초극한 다이어트 4대 기법"

하드웨어의 마이너한 한계까지 강제로 쥐어짜내는 극단적인 최적화 기법들입니다.

### 💡 [치트 6] RGB332 (8비트) 렌더링 ➔ 하드웨어 LTDC CLUT 출력 (RAM 150KB 세이브)
* **원인**: 일반적인 16비트 RGB565 프레임 버퍼를 사용할 경우 320x240 더블 버퍼링에 최소 **307 KB**의 RAM이 통째로 묶이게 됩니다.
* **해법**: 비디오 프레임 버퍼 포맷 자체를 **RGB332 (픽셀당 8비트/1바이트) 포맷**으로 절반으로 깎습니다.
  * 이렇게 하면 프레임 버퍼 하나당 76.8 KB로 줄어들어, 더블 버퍼를 구성해도 **153.6 KB**만 소모하여 즉각 **150KB 이상의 귀중한 RAM을 세이브**할 수 있습니다.
  * **출력 가속**: STM32H7 LCD 컨트롤러(LTDC)의 **하드웨어 CLUT(Color Look-Up Table) 룩업 기능**을 켜두어, LCD가 화면 주사(Scanout)를 할 때 하드웨어 수준에서 실시간으로 8비트 RGB332 데이터를 RGB565 아날로그 신호로 디코딩하여 패널로 쏩니다. CPU 오버헤드는 0%입니다.

### 💡 [치트 7] Coarse-grained Block Cycle 가산 (가상 클럭 연산 오버헤드 박멸)
* **원인**: 매 68000 어셈블리 지시어가 구동될 때마다 사이클 카운터 변수 가산(`cycles += 4;`)과 인터럽트 플래그를 체크하는 방식은 렌더러 루프의 수억 번의 연산 속에서 엄청난 속도 저하를 발생시킵니다.
* **해법**: 정적 재컴파일 번역 시, 분기문이 없는 최소 실행 단위 블록(Basic Block) 내의 모든 명령어 사이클을 미리 합산해 두고, **블록의 끝에서 단 한 번만 사이클을 가산**하는 Coarse-grained 동기화 기법을 도입합니다. 또한, 매 연산 시 인터럽트 대조를 하지 않고 분기 명령어(Branch)가 실행되는 지점에만 인터럽트를 확인합니다.

### 💡 [치트 8] LTDC 하드웨어 듀얼 레이어 오버레이를 통한 Z-Buffer 제거
* **원인**: 아케이드의 복잡한 레이어 우선순위(Priority)를 에뮬레이트하기 위해 소프트웨어 Z-Buffer(우선순위 대조 배열)를 RAM에 할당하고 픽셀별 대조 연산을 수행하면 RAM 대역폭이 찢어집니다.
* **해법**: CPS-1의 3개 배경 레이어 중 최하단 레이어와 중간 레이어는 STM32H7 LTDC가 제공하는 **하드웨어 듀얼 레이어 오버레이(Layer 1 & Layer 2)**에 각각 바인딩합니다. CPU는 최상단 스프라이트와 레이어만 한 버퍼에 렌더링하고, 투명 영역 합성 및 블렌딩은 디스플레이 컨트롤러가 실시간으로 처리하게 만듭니다.

### 💡 [치트 9] 오디오 믹서의 하드웨어 MAC (Multiply-Accumulate) 및 고정소수점 픽스
* **원인**: 효과음(ADPCM) 피치 시프팅 및 QSound 재생을 위해 부동소수점(Float) 계산이나 나눗셈을 돌리면 파이프라인 지연이 발생합니다.
* **해법**: 믹서 루프 내부의 모든 부동소수점과 나눗셈을 지우고, 비트 시프트(`>> 8` 또는 `>> 16`) 기반의 **16비트 정수 고정소수점 산술**로 전체 믹싱 공식을 재설계합니다.
  * ARM Cortex-M7의 하드웨어 MAC 연산기인 `SMLAL` (Signed Multiply Accumulate Long) 어셈블리 1사이클 명령어로 믹싱 루프를 최적화하여 오디오 믹싱 비용을 제로에 가깝게 수렴시킵니다.

## 4. 🛠️ 격리 하네스 환경 기반 "1회차 무결점 60fps 돌파" 프로토콜 (신규 추가)

실기 타겟에 바로 올려 시행착오를 거치며 프레임을 점진적으로 튜닝하는 대신, **PC 호스트 및 QEMU M7 정밀 하네스 환경(Harness framework)**에서 소스코드를 완벽히 격리 검증하여 1회차 실기 부팅부터 완성형 60fps에 다다르는 최첨단 통합 개발 검증 프로토콜입니다.

### 📋 단계 1: 독립 워킹트리 (`explore/cps1-feasibility`) 격리
* 메인 브랜치에서 완벽히 격리된 `explore/cps1-feasibility` 브랜치를 생성하여, 다른 코어 및 런처 바이너리의 오염 없이 CPS-1 독립 코어 및 정적 재컴파일러(Static Recompiler) 컴파일 옵션만을 추적합니다.

### 📋 단계 2: PC/SDL2 호스트 하네스를 통한 "Bit-identical" 검증
* `linux/Makefile.cps1` 및 `linux/cps1/` PC 하네스 환경에서 에뮬레이션을 돌립니다.
* **검증**: 기존 소프트웨어 에뮬레이션 인터프리터의 렌더링 출력(Framebuffer checksum)과 **C Static Recompiler가 컴파일된 결과물의 렌더링 출력을 프레임 단위로 1:1 대조(Diff)**합니다.
* **판정**: 한 프레임이라도 비트 불일치가 발생하면 Static Recompiler의 번역 버그로 판정하고, 호스트 환경의 디버거(GDB)를 통해 바이트 수준에서 추적하여 100% 무결점을 증명합니다.

### 📋 단계 3: QEMU M7 Rig (시뮬레이터 하네스)를 통한 물리 병목 사전 차단
* 32X 포트에서 사용된 QEMU `mps2-an500` 시뮬레이터 에뮬레이션 장부를 그대로 가져옵니다.
* **계측**: QEMU 상에서 천지를 먹다 2를 실행하고, M7 Instruction Histogram(명령어 빈도 프로파일러)을 돌려 **ITCM/DTCM 메모리 충돌과 오버헤드를 가상 환경에서 계측**합니다.
* **판정**: 프레임당 네이티브 Instruction Count를 **4.5M 이하**로 정밀 튜닝하여, 실기 60fps(340MHz/60 = 5.6M cycles 예산)에 대입 시 버스 Stall을 감안해도 충분히 60fps 고정이 나오는 지점을 시뮬레이터 상에서 미리 수학적으로 통과시킵니다.

### 📋 단계 4: QSound HLE 오디오 샘플 정확도 비교 검증
* QSound 드라이버 HLE 플레이어가 실시간 생성하는 오디오 PCM 버퍼 데이터와 원본 Z80 + QSound 소프트웨어 에뮬레이션이 합성한 PCM 버퍼 데이터를 오실로스코프 및 수학적 RMS 오차율 0% 레벨까지 대조하여 싱크 및 음장 효과를 완벽하게 일치시킵니다.

## 5. 결론
이 프로토콜을 통과하여 **"하네스 상에서 100% 검증된 무결점 코어"**를 기기에 주입한다면, 실기 첫 플래싱(1회차) 시점부터 튜닝 기간 없이 **즉시 고정 60프레임으로 구동하는 것**이 완벽하게 가능합니다.
