# 32X 기기 측정 이력 (2026-07-26 ~ 07-27)

이 문서는 **하루치 실험 전부의 기록**이다. 성공한 것보다 **실패한 것이 더 중요하다** —
다음 사람이 같은 헛발을 안 차게 하는 게 목적이다.

판정 요약은 `Core/Src/porting/md32x/CLAUDE.md`, QEMU 리그 기반 초기 최적화는
`docs/32X_PERFORMANCE_RESULTS.md`에 있다. 여기는 **기기 DWT 측정** 이력이다.

**결론 먼저: 둠 10 → 13~16fps(계측기 포함), 애프터버너 컴플리트 8fps. 성능 축 종료.**

---

## 0. 왜 "GBA 같은 묘수"가 없었나 — 이게 제일 중요한 절이다

GBA에서는 **M4A 믹서 HLE**가 게스트의 27~60%를 걷어냈다. 그 묘수가 성립한 조건은
[[principle-hle-wins-only-vs-interpreted-guest]]에 적힌 그대로다:

> **닌텐도가 공급한 공용 사운드 라이브러리(M4A)를 수백 개 게임이 공유한다.**
> 그래서 HLE 하나가 라이브러리 전체에 먹힌다. 그리고 그것은 **인터프리트되는
> 게스트 코드**를 **네이티브 코드**로 갈아끼우는 것이라 배수로 이긴다.

32X에는 **그 조건이 하나도 없다.**

| | GBA | 32X |
|---|---|---|
| 공용 엔진 | M4A (닌텐도 공급, 수백 게임 공유) | **없음** |
| 사운드 | 게임들이 같은 믹서를 링크 | 게임마다 자체 드라이버 (둠의 믹서는 `0x4e7ce`, 둠 전용) |
| 렌더 | 하드웨어 PPU | **게임의 소프트웨어 렌더러** (둠 `0x048000`, 둠 전용) |
| HLE 효과 범위 | 라이브러리 전체 | **그 게임 하나** |

32X는 "SH-2 두 개 + 프레임버퍼"만 주고 나머지는 게임이 알아서 하는 하드웨어다.
렌더러도 사운드 드라이버도 게임마다 다르다. **그러니 여기서 HLE는 전부 롬별 작업이고,
롬별 적용은 끝이 없다**(유저 판단, 0726). 묘수의 조건이 원천적으로 없다.

이 절을 읽고 "그래도 둠 렌더러를 HLE 하면?"이 떠오른다면 — 그건 32X 에뮬레이터가
아니라 **둠 포팅**이다. 그리고 그 일은 이미 D32XR이라는 이름으로 남이 해놨다(아래 §11).

## 1. 출발점의 착각 — "19.5fps"는 게임플레이가 아니었다

기존 기록: "ITCM 이동으로 둠 15 → 19.5fps". 그런데 실제 게임플레이는 **10fps**였다.

원인: 프로파일러 창이 **부팅 앵커**였다. `MD32X_PROFILE_FRAMES=64`가 부팅 직후 64프레임을
쟀고, 그건 **타이틀 화면**이다.

증거가 결정적이었다 — **세 번 연속 측정에서 샘플 수가 131,537로 완전히 동일**했다.
타이틀 시퀀스가 결정적이라 그런 것이고, 즉 우리는 같은 장면을 세 번 잰 것이었다.

**수정**: 워밍업 1200프레임(~20초) 후 창 개방, 모든 카운터를 개방 시점에 0으로.
"저장하고 재실행하세요" 같은 유저 안내로 때우려다 실무에서 안 지켜져서, **코드로** 고쳤다.

> **교훈 ①** 프로파일 창이 무엇을 재는지부터 확인하라. 재현성이 완벽하면 좋은 게 아니라
> **결정적인 구간을 재고 있다는 뜻일 수 있다.**

**대가**: 그 뒤로 덤프를 받으려면 유저가 **20초 이상 실제로 플레이**해야 한다. 짧게 켜면
파일이 아예 안 생긴다. (SNES 세션도 같은 수정을 했고 같은 부작용을 안았다.)

## 2. pcwall 프로브 — 창을 다섯 번 옮겼다

게스트 PC를 32명령마다 샘플링해 DWT 델타를 PC 페이지에 귀속시키는 프로브.
`cpu/sh2/mame/sh2pico.c`. 조준 이력이 그 파일 주석에 남아 있다.

| 패스 | 창 | 결과 |
|---|---|---|
| 1 | 1KB × 64, ROM 0~64K | **rom<64K = 0.0%** — QEMU가 지목한 루프가 기기에선 완전히 식어 있었다 |
| 2 | 64KB × 64, 전체 4MB | msh2 77.6% = 페이지 0x030000, 17.3% = 0x040000 |
| 3 | 2KB × 64 | msh2 51.4%가 단일 페이지 0x036000 — **그런데 이게 타이틀이었다**(§1) |
| 4 | 2KB × 64, 게임플레이 창 | **0x036000이 0.7%로 증발.** 새 핫셋 = 0x04d800 37.7% + 0x049000 34.5% |
| 5 | 128B × 64 | **msh2 35.0%가 단일 128바이트 페이지 `0x0204df00`** |

> **교훈 ②** 패스 3의 결과로 최적화했다면 하루를 통째로 버렸을 것이다.
> **패스 4에서 51.4%가 0.7%가 됐다.** 장면이 다르면 과녁도 다르다.

> **교훈 ③ QEMU 명령 히스토그램은 기기 과녁이 아니다.** 패스 1이 그걸 증명했다 —
> QEMU가 "여기가 핫하다"고 지목한 루프 두 개(`0x02005fa6`, `0x020023a8`)의 기기 지분은
> **0.0%**였다. 명령 수 ≠ 기기 사이클.

## 3. ✅ 성공 ① — 마스터의 프레임대기 스핀 폴드 (프레임 −18.8%)

패스 5가 지목한 128바이트를 디스어셈블(`tools/` 밖의 미니툴 `dasm32x`)하니:

```
0x04df26:  CMP/EQ R0,R2
           MOV.L  @R1,R0      ; R1 = SDRAM 0x06001170 (VInt ISR이 증가시키는 프레임 카운터)
           BT/S   -2
           AND    R3,R0
```

= **마스터 SH-2의 프레임 대기 루프**. 매 프레임 렌더를 마치고 다음 VInt를 기다리는 자리.

왜 기존 fastloop가 못 잡았나 — 두 가지:
1. SDRAM은 직접 매핑이라 **poll-detect 훅이 없다**
2. fastloop 프리필터에 **`BT/S`(0x8d) 케이스가 없었다**(BF/BFS/BRA만)

**수정**: fastloop에 BT/S SDRAM 폴 케이스 추가. 설계 규칙 두 가지를 지켰다 —
- **오페코드 지문으로 인식**(4-오페코드 패턴 + SDRAM 정렬 롱 + 레지스터 제약).
  롬 CRC로 게임을 식별하지 않는다 → 범용
- **이 인터프리터 기준 사이클 정확**(반복당 정확히 5, mame의 "BT/S는 양쪽 경로에서
  딜레이 슬롯 실행" 의미론 미러링), 종료 시 실제 BT/S가 미취득으로 디스패치되어
  **상태 비트동일**

**게이트**: QEMU M7 리그, `RIG_TRACE_CKS`로 매 프레임 프레임버퍼 체크섬 → **402프레임
비트동일**(폴드 ON vs fastloop 전체 OFF).

**기기 실측**: 해당 페이지 **35.0% → 0.2%**. 프레임 wall 35.23M → 28.61M = **−18.8%**.

## 4. ❌ 실패 ① — 메모리 디스패치 원장: 쓰기 경로는 범인이 아니었다

가설: "모든 SH-2 write가 간접 호출이니 거기가 비쌀 것이다." 그럴듯했다.

**측정**(원장 프로브, 핸들러 호출을 DWT로 감싸 계수):

```
msh2  read_h 8,746회  write8 4,265  write16 467,092  write32 249,243
      => 64프레임 1,276M 사이클 중 14.3M = 1.1%   (호출당 15-20사이클, 프로브 자기비용 10 포함)
ssh2  자기 wall의 14.9%, 그런데 ssh2는 프레임의 9.4% => 프레임 기준 1.4%
```

**판정: 축 사망.** 원장 코드는 삭제하고 수치만 `pico/32x/memory.c` 주석에 남겼다.

> **교훈 ④** "그럴듯한 병목"은 재기 전엔 아무것도 아니다. 이 가설 하나 재는 데 든
> 비용(프로브 작성 + 기기 왕복 1회)이, 안 재고 최적화했을 때 버릴 시간보다 훨씬 쌌다.

## 5. ✅ 성공 ② — ROM 오페코드 페치 인라인 (리그 −17.7%)

창을 다시 넓히니(16KB × 64, ROM 0~1MB) 결정적인 줄이 나왔다:

```
msh2:  rom_win=100.0%  sdram=0.0%
```

**둠의 마스터는 SDRAM에서 0%, 카트 ROM에서 100% 실행된다.** 그런데 오페코드 페치
fast path는 **SDRAM 전용**이었다("32X 코드는 SDRAM에 산다"는 주석과 함께). 즉 프레임당
~17만 번의 페치가 전부 cross-TU `p32x_sh2_read16` 호출을 물고 있었다.

**수정**: ROM(0x02/0x22)도 인라인. `gnw_sh2_rom_fetch_mask`는 CS1 read16 맵 엔트리의
마스크 그대로라 **맵과 바이트 동일**하고, SSF2 뱅킹으로 그 엔트리가 핸들러가 되면
0이 되어 **자동 비활성**된다.

**덤**: fastloop 프리필터 5비교 → 1비교. 후보 4개(`0x8980/8b80/8d80/8f80`)가 전부
"n의 bit3와 bit0이 선 0x8n80"이라 `(op & 0xf980) == 0x8980` 하나로 덮인다.
**전 65,536 오페코드 동치 증명**.

**게이트**: 402프레임 비트동일, guest insn 동일. 호스트 명령/프레임 **27.03M → 22.26M
(−17.7%)**, 메뉴 프레임 −11.5%.

## 6. ❌ 실패 ② — 데이터 로드까지 인라인 (리그가 기기 전에 걸러냄)

같은 논리로 `RB/RW/RL`(게스트 데이터 로드)도 인라인해봤다.

**리그 측정**: 체크섬 402프레임 비트동일(정확함), 그런데 **호스트 명령 +3.6%**.

이유: 두 개의 비교를 **모든 로드가** 무는데 대부분이 SDRAM/ROM에 안 떨어진다.
게다가 오버레이 텍스트가 ~2KB 늘어나는데 그때 MD32X 마진은 **328바이트**였다.

**판정: 기각. 기기에 올리지 않았다.** 리그 20분이 기기 왕복 한 번과 회귀 하나를 막았다.

> **교훈 ⑤ 리그를 정합성 게이트로만 쓰지 말고 후보 걸러내는 데 써라.**
> 단, 리그의 "명령 수"는 **방향 지표이지 크기 지표가 아니다**(교훈 ③).

## 7. ❌ 실패 ③(가설) — 외장 플래시 지연: 기각

가설: "ROM이 QSPI XIP니까 페치가 캐시 미스로 수십 사이클 걸릴 것이다. 그러면 ROM을
RAM에 캐싱해야 한다."

이건 값비싼 길이었다(RAM 예산 싸움). **재고 나서 가기로 했다.**

**프로브**: 31분의 1 페치를 DWT 쌍으로 감싼다. 주기를 **소수**로 잡은 이유 —
2의 거듭제곱은 게스트의 타이트 루프(4명령)나 D-캐시 라인(16하프워드)과 정렬돼
**항상 같은 명령만 샘플링**하게 된다.

**측정**(두 개의 완전히 다른 장면):

| | 가벼운 장면 | 무거운 장면 |
|---|---|---|
| 페치 net | **10.3 cyc** | **10.4 cyc** |
| 지분 | 10.1% | 12.1% |

**판정: 기각.** QSPI 미스면 40~100사이클이 나와야 한다. 평균 10이면 **D-캐시가 흡수
중**이다. → **ROM을 RAM에 캐싱하는 축은 닫힘.** RAM 예산 싸움을 안 해도 됐다.

> **교훈 ⑥ per-event 비용은 장면에 안 흔들린다.** 10.3 vs 10.4 — 이게 **기기에서
> A/B를 할 수 있는 유일한 종류의 숫자**다(교훈 ⑧ 참조).

## 8. 비용 모델이 닫혔다 — 여기서 판정이 갈렸다

데이터 접근에도 같은 브래킷(29분의 1, 페치와 다른 소수)을 걸어 **명령 1개의 비용을
전부 분해**했다.

```
msh2 명령당 94.0 사이클:
  오페코드 페치   10.3 × 1.00 = 10.3
  게스트 로드     29.3 × 0.37 = 10.8
  게스트 스토어   38.5 × 0.06 =  2.3
  ─────────────────────────────────
  메모리 합계                   23.4   (25%)
  인터프리터 디코드/실행       ~70     (75%)
```

**메모리는 4분의 1뿐이고, 나머지 4분의 3은 인터프리터 자신이다.** 그리고 인터프리터
코드는 **이미 ITCM(무대기)에서 돈다**(예전 +30% 이동).

이 표가 나온 순간 남은 선택지가 전부 정해졌다 — 배치로 얻을 건 다 얻었고, 디코드/실행을
줄이려면 인터프리터를 다시 쓰거나 해석을 그만두거나(다이나렉) 둘 중 하나다.

## 9. ✅ 성공 ③ — 게스트 버스 진입점 ITCM (그리고 **조용한 실패**를 맵이 잡은 이야기)

맵을 보다 발견했다:

```
000023b0 t __md32x__p32x_sh2_read16_veneer
00002390 t __md32x__p32x_sh2_write16_veneer
...
```

**인터프리터는 ITCM(0x0)에 있는데 게스트 버스 진입점 6개는 RAM_EMU(0x24000000)에 있었다.**
603MB 거리라 `BL`의 ±16MB를 벗어나서, 링커가 함수마다 롱브랜치 트램폴린을 깔았고
**게스트가 로드/스토어할 때마다 간접 점프**를 물었다.

**1차 시도가 조용히 실패했다.** ITCM 출력 섹션에 `.text.p32x_sh2_read8` 등을 나열했는데,
**`.overlay_md32x`가 먼저 매칭해서 이미 삼킨 상태**였다. 결과: ITCM 규칙이 아무것도 못
잡고, **링크 성공 · 부팅 정상 · 베니어 그대로.**

SNES 세션이 자기 링커 주석에 정확히 이 경고를 적어놨었고, 그걸 읽고도 밟았다.
**맵을 확인했기 때문에** 잡았다.

**수정**: GNU ld는 입력 섹션을 이름으로 제외 못 한다 → 소스에서 전용 섹션명을 준다
(`GNW_SH2BUS = __attribute__((section(".itcm_sh2bus")))`, `GNW_32X_CORE` 가드).
**리그 링커 스크립트도 같이 claim**해야 고아가 안 된다.

**검증**: 핸들러 6개가 `0x2618~0x2720`(ITCM), **ITCM쪽 베니어 0**. 멀어진 건 드문 방향
(sh2soc DMA · IRQ 벡터 · XIP 냉코드). 부수효과로 RAM_EMU 마진 328 → 520바이트.

> **교훈 ⑦ 링커 배치는 "빌드됐다"로 확인하지 말고 맵으로 확인하라.**
> 매칭 안 되는 규칙은 에러가 아니라 **무동작**이다.

⚠️ **이 변경의 크기는 측정되지 않았다.** 최적화와 데이터접근 프로브를 같은 빌드에
넣는 바람에 분리가 불가능했다. 구조는 맵으로 증명됐지만 숫자는 모른다. **설계 실수다.**

## 10. ❌ 실패 ④ — SH2 레지스터 파일 DTCM 이동: 만들고, 재고, 되돌렸다

가설(꽤 그럴듯했다): 명령마다 `r[]/pc/ppc/sr/icount/delay`를 건드리고, 게스트 로드/스토어가
`sh2`를 넘기는 외부 호출이라 컴파일러가 호출마다 스필/리로드한다. 그 상태가 AXI SRAM에
있으니 DTCM(무대기)으로 옮기면 **+9~17%**.

전부 제대로 만들었다 — 전용 섹션명(§9 교훈 적용), NOLOAD(안 그러면 12KB가 intflash에
실린다), 코어 진입 시 명시적 memset(NOLOAD는 **아무도 0으로 안 채운다**), 리그 링커
스크립트 수정(독립 섹션으로 뒀다가 "스타트업이 `_sdata.._edata`만 복사 → 로드 안 됨"을
리뷰에서 자가 발견), 리그 120프레임 비트동일.

**기기 측정** (배치는 살아 있었다 — diag에 `sh2 dtcm zeroed: 12032 B`):

| | DTCM 없음 | DTCM 있음 |
|---|---|---|
| cyc/insn | 94.0 | 92.1 |
| **페치 net** | 10.3 | **10.3** (동일) |
| read net | 29.3 | 30.2 |
| write net | 38.5 | 36.9 |
| fps | 13.1 | 13.0 |

**2%는 장면 편차 안이다**(같은 코드로 85.7~101.6을 오간 지표). per-event 비용은 평평.

**이유**: **D-캐시가 이미 그 일을 하고 있었다.** SH2 컨텍스트의 핫 부분은 ~100바이트이고
매 명령 접근되니 절대 밀려나지 않는다. 무대기로 옮겨봐야 히트 2~3사이클이 1사이클 될 뿐.

**되돌린 결정타는 이득 부재가 아니라 값이었다**: DTCM 힙 12KB를 **모든 코어에서 상주로**
먹는데, 남는 78,208바이트에 PICO-8이 64KB + i18n 캐시가 들어간다. 여유 몇 KB에,
**NULL 대신 assert로 죽는 공유 할당자**다.

> **교훈 ⑧ 기기 덤프끼리는 장면이 다르면 A/B가 안 된다.** `cyc/insn`은 **코드가 같은데도**
> 85.7 ↔ 101.6을 오갔다(무거운 장면일수록 지역성이 좋고 슬라이스가 길어서 **오히려 싸다**).
> 장면에 안 흔들리는 건 **per-event 비용뿐**이다(교훈 ⑥).

> **교훈 ⑨** 같은 날 SNES 세션도 ITCM 확장을 만들고 재고 되돌렸다(fps 41.3 → 40.9).
> 결론이 같다: **I-캐시도 D-캐시도 이미 제 일을 하고 있다.** 이 기기에서 "캐시 우회"
> 최적화는 기대만큼 안 나온다.

## 11. ❌ 다이나렉 — 열거로 닫힘 (게으름이 아니라 물리)

2배가 되려면 해석을 그만둬야 한다. picodrive에는 **SH-2 다이나렉이 이미 있다**
(`DRC_SH2`) — 다른 기기에서 picodrive가 빠른 이유가 그것이다.

번역 캐시가 필요하다. 둠의 핫 SH-2 코드가 수십 KB, ARM 출력은 보통 4~8배 → **256~512KB**.

**RAM_EMU 692.5KB를 통째로 열거했다:**

```
520.0 KB  gnw_32xmem   = 32X SDRAM 256K + DRAM 프레임버퍼 2×128K   ← 하드웨어 규격
136.4 KB  PicoMem      = 68K RAM 64K + VRAM 64K + CRAM/VSRAM/zram  ← 하드웨어 규격
 11.8 KB  sh2s         = SH2 구조체 2개
  6.9 KB  PsndBuffer / 5.4 KB m68k / 나머지
```

**656KB가 문자 그대로 에뮬레이트되는 콘솔의 RAM이다.** 깎을 게 없다.
ITCM 여유 4.3KB, AHB 320바이트, DTCM 힙은 PICO-8이 64KB를 쓴다.

**판정: 자리가 없어서 닫힘.** 추측이 아니라 열거로 확인된 사실이다.

## 12. ⏸ 안 판 방 — 68K 12.9%

msh2 밖 32% 중 제일 큰 조각. **프로브는 소스에 있다**(`MD32X_DEVICE_PROFILE`,
`cpu/gwenesis68k/m68kcpu.c`): 게스트 사이클 run vs skip, 명령 수, 게스트 사이클당 기기
사이클, PC 히스토그램(32KB × 32).

picodrive에는 **이미 68K 유휴 스킵이 있다** — `m68k_poll_detect`가 68K의 **32X 레지스터**
반복 읽기를 잡으면 `SekSetStop`. 그래서 질문은 하나: **`skip_pct`.**

- 100 근처 → 이미 동작 중, 남은 12.9%는 진짜 연산, 축 종료
- 0 근처 → 둠의 대기가 32X 레지스터 폴이 아니라 감지 밖 → **§3의 폴드가 갈 자리가 하나 더**

최선의 경우에도 ~7%라, 애프터버너 8fps 판정이 난 뒤엔 기기 왕복 값어치가 없어 남겼다.

## 13. ⏸ 안 잰 것 — D32XR, 그리고 **2D 타이틀**

**D32XR (Doom 32X Resurrection)**: 둠 32X를 통째로 재작성한 커뮤니티 포트. 같은 하드웨어에서
훨씬 적게 일한다. **우리 코드 0줄**, 롬만 바꿔 같은 장면 비교. 2배급 후보는 이것뿐이었다.
끝내 안 됐다.

**2D 타이틀 — 이게 제일 정직한 구멍이다.** 우리가 잰 건 둠과 애프터버너 컴플리트인데
**둘 다 SH-2가 소프트웨어로 3D/스케일링을 도는 최악 부류**다. 카오틱스 · 모탈컴뱃 II ·
NBA Jam TE · 프라이멀 레이지는 32X를 **주로 색·스프라이트 확장으로만** 쓰고 SH-2는 훨씬
적게 돈다. **완전히 다른 부하이고 한 번도 안 쟀다.**

**"코어가 못 쓸 물건이냐, 3D만 못 쓰냐"가 여기서 갈린다.** 30초짜리 확인이다.

## 14. 도구·운용에서 배운 것 (이게 시간을 제일 많이 먹었다)

- **`make docker`는 커맨드라인 변수를 통째로 버린다.** 안쪽 make 명령줄이 하드코딩돼 있어
  `MD32X_DEVICE_PROFILE=1`도 `ENABLE_BOOT_OC=1`도 조용히 사라진다. 그래서 "마진 1,012B
  확보" 판정이 **CI가 굽는 것과 다른 바이너리**의 숫자였다(진짜는 328B).
  → **`make release DOCKER=1 <플래그>`만 쓸 것.** 그리고 **검증 후 `nm`으로 그 노브의
  심볼이 ELF에 실제로 있는지 확인**하라 — 맵 grep은 오버레이 BSS 심볼을 놓친다.
- **프로파일러는 공짜가 아니다.** `MD32X_DEVICE_PROFILE=1`이 명령당 94 중 ~16(약 17%)을
  먹는다. **오늘 유저가 본 fps는 전부 세금 낀 값이었다.** 최종 릴리즈에서 제거했다.
- **리그 `RIG_TIMEOUT`(기본 1800s)이 게임플레이 실행을 조기 킬한다.** 게임플레이 프레임은
  22~44M 호스트 명령이라 프레임당 분 단위다. `RIG_TRACE_CKS`로 매 프레임 찍으면 잘려도
  부분 스트림을 비교할 수 있다 — **리포트를 루프 끝에서만 찍으면 아예 못 본다.**
- **QEMU 접근 인구조사(`RIG_MEM_MIX`)는 접었다.** 게임플레이 도달에 13분 + 프레임당 4분이라
  타임아웃을 두 번 넘겼고, 무엇보다 **QEMU는 캐시 모델이 없어 접근을 세도 값을 못 매긴다** —
  그게 진짜 질문이었다. 기기 프로브가 대체했다.
- **`pkill -f <스크립트명>`은 자기 명령줄도 매치해 자살한다.** `pgrep | awk | xargs kill`.
- **소프트플로트 리그 함정**(SNES 세션 제보, 32X는 해당 없음): `run_snes.sh`가
  `-mfloat-abi=soft`라 부동소수 관련 변경이 **−27.95%로 보였는데 하드플로트 기기에선
  +0.93% 순손실**이었다. **부호까지 뒤집힌다.** `run_32x.sh`는 처음부터 하드플로트
  (`-mfloat-abi=hard -mfpu=fpv5-d16`)라 노출이 없었다.

## 15. 최종 성적표

**출하하고 남긴 것 3건**

| 변경 | 근거 | 검증 |
|---|---|---|
| 마스터 프레임대기 스핀 폴드 | pcwall이 단일 128B 페이지 35% 지목 | 기기 35.0%→0.2%, 프레임 −18.8%, 리그 402f 비트동일 |
| ROM 오페코드 페치 인라인 | msh2가 sdram 0% / ROM 100% 실행 | 리그 402f 비트동일, host insn −17.7% |
| 게스트 버스 진입점 → ITCM | 맵에 베니어 6개 실재 | 맵에서 ITCM쪽 베니어 0, 리그 120f 비트동일 |

**측정으로 닫은 축 7건** — 쓰기경로(1.1%) · 데이터로드 인라인(+3.6%, 리그가 기각) ·
플래시 지연(페치 10.4cyc 고정) · **다이나렉(RAM 열거)** · ITCM(이미 소진) ·
**DTCM(만들고 재고 되돌림)** · QEMU 인구조사(캐시 모델 없음)

**되돌린 것 2건** — 둘 다 "될 것 같아서" 남기지 않았다.

**기기 실측** — 둠 10 → 13~16fps(계측기 포함, 제거 시 ~15) · **애프터버너 컴플리트 8fps**

애프터버너가 마지막 가설("둠이 최악이고 다른 게임은 괜찮다")을 깼고, 거기서 축을 닫았다.
