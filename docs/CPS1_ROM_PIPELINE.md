# CPS-1 ROM 파이프라인 스펙 — game-and-what (rpi-genie5)

> ## ⚠️ 이 문서의 §3(변환기)은 폐기됐다 — 2026-07-21
> `.cps1`은 **표준 포맷이 아니라 이 세션에서 내가 만든 것**이고, **불필요한 것으로
> 판명됐다.** 전제가 틀렸다: "MAME의 8칩 인터리브를 쓰려면 4MB로 조립해야 한다"고
> 봤지만, 인터리브는 순수한 주소 산술이다.
> ```
> half = (off >= 0x200000);  o = off - half*0x200000
> chip = half*4 + (o % 8)/2;  index = (o / 8)*2 + (o % 2)
> ```
> 실측 검증: wofj 실제 칩으로 **랜덤 20만 오프셋이 조립본과 바이트 단위 완전 일치,
> 불일치 0건**. 구현은 `cps1_rom.c`의 `cps1_gfx_chip_byte()`.
>
> **그래서 올바른 배치는 "MAME 롬셋을 폴더에 풀어두는 것"뿐이다** — 변환기도,
> 캐시도, 내가 만든 컨테이너도 필요 없다. 필요한 건 "어느 파일이 어느 슬롯인가"를
> CRC로 식별하는 표 하나이고 그건 이미 패커에 있다.
>
> 아래 §3은 그 판단이 나오기 전의 기록으로 남긴다. §2의 폴더 구조와 §5의 권한
> 함정은 그대로 유효하다.


> 작업 지시서. 대상: rpi-genie5의 `game-and-what`(= `/home/pi/app/ganda-rpi`) 롬 관리 프로젝트.
> 목적: CPS-1(캡콤 아케이드) 롬이 도착했을 때 **손대지 않고 기기용으로 변환·배치**되는 구조와 변환기를 미리 만들어 둔다.

---

## 0. 절대 하지 말 것 (먼저 읽어라)

**인터넷에서 롬을 받아오지 마라.** 검색·다운로드·크롤링 전부 금지다. 이 작업의 산출물은
**구조와 변환기**이지 롬이 아니다. 롬 파일 자체는 **유저가 직접 공급**한다.

지금 rpi-genie5 라이브러리에는 CPS-1 롬이 **없다**(확인 완료: `roms/`에 콘솔 32종뿐, 아케이드
디렉토리 자체가 없음). "천지를 먹다"로 검색되는 `roms/nes/천지를 먹다 2`, `roms/snes/천지를
먹다 - 삼국지 군웅전`은 **전혀 다른 하드웨어의 다른 게임**이다. CPS-1 아케이드판(`wof`)이
아니므로 대체재로 쓰지 마라.

---

## 1. 배경 (왜 이게 필요한가)

G&W retro-go에 CPS-1 코어를 포팅 중이다. 68000은 Musashi로 교체 완료했고
(`explore/cps1-feasibility` 브랜치, `bcdd27eb`), CPU 비용은 프레임 예산의 **18.3%**로 실측됐다
(`6f768763`). 남은 미지수는 **그래픽 축**인데, 이건 합성 데이터로는 절대 예측이 안 되고
**실제 게임 롬**이 있어야만 실측된다. 그래서 롬이 도착하는 즉시 돌릴 수 있게 파이프라인을
먼저 세운다.

타깃 게임: **천지를 먹다 II (Warriors of Fate)**, MAME 롬셋 이름 `wof` 계열.

---

## 2. 라이브러리 배치 규칙 (확정)

**MAME 롬셋을 폴더에 풀어둔다. 그게 전부다.** 변환 산출물도, 사이드카 파일도,
전용 확장자도 두지 않는다 — §0의 회수 사유대로 인터리브가 주소 산술로 풀리므로
조립본이 필요 없다.

기존 관례와 같다: 단일 파일 기종은 `roms/<시스템>/<게임>.<확장자>`, 복수 파일
기종(SegaCD, PC Engine CD)은 `roms/<시스템>/<게임>/…` 폴더. CPS-1은 **폴더 방식**이고,
지역 병기는 `roms/vb/` 관례를 따른다.

```
data/library/public/roms/cps1/
├── 천지를 먹다 2 (Warriors of Fate) (World)/     ← wof.zip(=실제로는 wofr1) 풀어둔 것
│   ├── tk2e_23b.rom  tk2e_22b.rom                  68000 프로그램
│   ├── tk2_gfx1.rom … tk2_gfx8.rom                 GFX 8칩
│   ├── tk2_qa.rom                                  QSound Z80
│   └── tk2_q1.rom … tk2_q4.rom                     QSound 샘플
├── 천지를 먹다 2 (Warriors of Fate) (Japan)/     ← wofj.zip 풀어둔 것(고유분 6칩만)
├── wof.zip / wofj.zip                            ← MAME 정본, CRC 대조 기준으로 보존
└── (`.cps1` 파일은 두지 않는다 — 있으면 지운다)
```

**두 가지를 반드시 지킨다:**

1. **폴더 이름은 사람이 읽는 이름, 파일 이름은 MAME 원본 그대로.** 칩 파일명은
   절대 바꾸지 마라. 다만 기기는 파일명이 아니라 **CRC32로 슬롯을 식별**한다 —
   같은 게임의 롬셋이라도 덤프 세대에 따라 파일명이 다르고(`tk2e_23b.rom` vs
   `tk2j23c.bin`), **파일명 숫자가 슬롯 순서와 다른 실례도 있다**: wof의
   `tk2_gfx2.rom`은 3번 슬롯, `tk2_gfx3.rom`이 2번 슬롯이다. 파일명으로 매핑하면
   비트플레인 두 쌍이 교차돼 그래픽만 조용히 깨진다.

2. **클론셋은 부모 폴더가 있어야 완전하다.** wofj는 split set이라 고유분 6칩만
   들고 있고 gfx 하위 4칩·z80·QSound 샘플은 부모(World)에서 온다. 자식 폴더만
   두면 실행 불가다. **부모와 자식은 항상 같이 둔다.**

`covers/cps1/`도 같은 이름 규칙으로 둔다.

## 3. (폐기됨) 변환기 — 문서 맨 위의 회수 사유 참조

> 아래는 폐기 전 기록. 구현하지 마라.

`wof` MAME 롬셋(폴더 또는 zip) → 단일 `.cps1` 파일.

### 3-1. 롬셋 정의는 반드시 MAME 소스에서 확인해라 (추측 금지)

내 기억으로 wof는 maincpu 4칩 `ROM_LOAD16_BYTE` 인터리브 + gfx `ROM_LOAD64_WORD` +
**QSound**(OKI6295 아님) 구성이지만, **이걸 믿고 짜지 마라.** `mamedev/mame` 마스터의
`src/mame/capcom/cps1.cpp`에서 `ROM_START( wof` 블록을 직접 읽어 확인해라.

⚠️ **WebFetch/WebSearch는 이 파일에서 실패한다** — 분명히 있는 내용을 "없다"고 답한 전례가
있다(`docs/CPS1_MAME_ALIGNMENT.md` 머리말). **`curl`로 raw 파일을 받아 로컬에서 grep**해라.
그게 실제로 통한 방법이다.

확인할 것: 각 리전의 칩 목록·크기·로드 매크로(`ROM_LOAD16_BYTE` / `ROM_LOAD16_WORD_SWAP` /
`ROM_LOAD64_WORD` 등)·오프셋·인터리브 간격, 그리고 CPS-B 칩 종류(wof는 `CPS_B_21_QS1`,
레지스터 베이스 `0x800140` — 우리 `cps1_core.c`가 이미 이 값을 쓴다).

### 3-2. 출력 포맷 (기기가 읽는 형식)

전부 **리틀엔디안**, 오프셋은 파일 선두 기준, 각 리전은 4바이트 정렬.

| 오프셋 | 크기 | 필드 |
|---|---|---|
| 0x00 | 4 | 매직 `"CPS1"` |
| 0x04 | 2 | 포맷 버전 = 1 |
| 0x06 | 2 | 플래그 (bit0 = prg가 16비트 바이트스왑됨) |
| 0x08 | 16 | 롬셋 이름 ASCII, NUL 패딩 (`"wof"`) |
| 0x18 | 4 | prg_offset |
| 0x1C | 4 | prg_size |
| 0x20 | 4 | gfx_offset |
| 0x24 | 4 | gfx_size |
| 0x28 | 4 | z80_offset |
| 0x2C | 4 | z80_size |
| 0x30 | 4 | snd_offset  (QSound 샘플 / OKI ADPCM) |
| 0x34 | 4 | snd_size |
| 0x38 | 4 | cps_b_id  (wof = CPS_B_21_QS1을 나타내는 정수) |
| 0x3C | 4 | payload CRC32 |
| 0x40 | … | payload (prg, gfx, z80, snd 순서) |

리전 4개는 우리 `Core/Src/porting/cps1/cps1_rom.h`의 `cps1_rom_t`(prg/gfx/z80/oki)와 1:1로
대응된다. 기기는 헤더만 읽고 4개 포인터를 꽂으면 끝나야 한다.

### 3-3. ★prg는 반드시 16비트 바이트스왑해서 저장해라 (이걸 틀리면 조용히 다 깨진다)

기기의 68000은 Musashi인데, base 포인터로 매핑된 영역을
`*(uint16*)(base+off)` / `base[off^1]`로 읽는다(`macros.h`의 LSB_FIRST 분기). 리틀엔디안
기기에서 이게 맞으려면 **프로그램 ROM이 16비트 단위로 바이트스왑되어 저장**돼 있어야 한다.
메가드라이브가 런처에 `GAME_DATA_BYTESWAP_16`으로 등록된 이유가 정확히 이것이다.

- **prg**: 인터리브로 68000 순서(빅엔디안) 이미지를 만든 뒤, **워드 단위로 바이트 스왑**해서 기록.
  플래그 bit0을 1로 세워라.
- **gfx / z80 / snd**: 스왑하지 마라. gfx는 우리 쪽 `cps1_rom_decode_tile`이 비트플레인
  스위즐을 처리하므로 **디인터리브된 네이티브 칩 순서**로 넣으면 된다. z80/snd는 바이트 스트림이다.

### 3-4. 검증까지 포함해라 (변환만 하고 끝내지 마라)

만든 `.cps1`에 대해 최소 이걸 자동 검사하고 결과를 출력해라:

1. **리셋 벡터 sanity**: prg를 68000 순서로 되돌렸을 때 `0x000000`의 초기 SSP와 `0x000004`의
   초기 PC가 말이 되는 값인가(PC가 prg 범위 안, 짝수). 우리 쪽에 이미
   `cps1_rom_check_reset_vector()`가 있으니 같은 판정을 쓰면 된다.
   **이게 통과 못 하면 바이트스왑 방향이 반대인 것**이다. 가장 흔한 실패 모드다.
2. 각 리전 크기가 MAME 정의의 `ROM_REGION` 크기와 일치하는가.
3. 개별 칩 덤프의 CRC32가 MAME 롬셋 정의의 값과 일치하는가(칩 파일이 온전한지).
4. payload CRC32 기록.

변환기 위치는 game-and-what 프로젝트 안 도구 디렉토리에 두고, 재실행 가능하게(멱등) 만들어라.

---

## 4. 롬이 도착하면

`roms/cps1/<게임명 (지역)>/`에 원본 칩을 풀어두고, **각 칩의 CRC32가 MAME 롬셋
정의와 일치하는지만 확인**해서 보고해라. 변환은 없다. 클론셋이면 부모 폴더가
같이 있는지, 그리고 둘을 합쳤을 때 필요한 CRC가 전부 있는지 확인해라.

## 5. 권한 함정 (RPi5 쓰기)

`data/` 소유는 **1001:1001**(컨테이너 내부 유저)인데 ssh 로그인 유저는 `pi`(1000)다.
scp 직접 쓰기가 안 된다. 기존 방식대로:
```
tar cf - <파일들> | ssh rpi-genie5 'sudo tar xf - -C <dst> && sudo chown -R 1001:1001 <dst>'
```
