The Commodore 64 core is written in C++. The launcher is C. They share one ELF
and one internal-flash budget. One day the C++ core's exception-handling
tables — generated by the compiler for `throw`/`catch` support that the core
never actually uses — quietly migrated out of the core's overlay and into the
launcher's resident section, eating **5.6 KB** of an internal-flash budget that
had **44 bytes** free.

This is the story of a leak between two languages, two linker sections, and
two completely different ideas of what "resident" means — and of how every
other C++ core in the firmware had a defence against it, except this one.

## The budget

Internal flash on the STM32H7B0 is tight. The launcher — the always-resident
shell that handles the UI, the SD card, the input, the audio, the boot path
— lives in a 128 KB or 256 KB bank (depending on `INTFLASH_BANK`), and we
were **44 bytes from the wall**. Every feature added (a new string, a new
menu item, a new scene for the Clock app) had to be paid for by removing
something else. The C64 port was the straw that broke it: after merging the
Frodo C64 emulator, the release link overflowed by 32 bytes. The tag build
caught it. (The pull-request build did not, because it links against `main`,
which lacks the clock features — a CI gap worth its own story.)

I went looking for 32 bytes. I found 5.6 kilobytes.

## What C++ leaves behind

When `arm-none-eabi-g++` compiles a C++ file, it emits two kinds of sections
alongside the code:

- **`.ARM.extab`** — the exception specification tables (which types a
  function can throw).
- **`.ARM.exidx`** — the index tables that let the runtime unwind the stack
  to actually deliver a `catch`.

These are *required* if the code uses exceptions. They are also *generated*
if the code merely *could* use exceptions — which, for stock g++, means
"unless you pass `-fno-exceptions`." And they pull in **`libgcc`'s unwind
runtime** (`unwind-arm.o`, `pr-support.o`) — the actual code that walks the
tables at throw-time. So even a C++ file with zero `throw` or `catch`
anywhere in it can drag several KB of tables plus a KB of runtime into the
link, unless you tell the compiler you don't need them.

Frodo (the C64 emulator we use) is old C++. It has classes, constructors,
virtual methods. It has **zero** `throw` or `catch` anywhere — I grepped
every file under `Core/Src/porting/c64/frodo/`. But g++ does not know that
from a grep. It generates the tables because that is its default.

## Where the tables went

Every emulator core in this firmware is an **overlay** — linked at the same
RAM address (`__RAM_EMU_START__`), loaded one at a time, never co-resident.
The overlay's code and data live in their own sections (`.overlay_c64`,
`.overlay_c64_bss`, etc.) and are extracted into a standalone `.bin` on the
SD card. They do **not** live in internal flash. They are not resident.

But the `.ARM.extab` / `.ARM.exidx` sections are not `.overlay_*` sections.
Without an explicit linker rule, the linker looks at them, sees no
`overlay_c64` prefix, and falls back to the **default output section** —
which, for `.ARM.*`, is the **resident** `.ARM` block in internal flash,
next to the launcher's own tables.

So Frodo's exception tables — for exceptions Frodo never throws — landed in
the launcher. And they brought the libgcc unwind runtime with them, because
the runtime is what reads those tables. Five and a half kilobytes of
internal flash, gone, on a budget with forty-four bytes to spare. While the
C64 overlay, where the tables *should* have lived, was unaffected.

## Why every other C++ core was fine

We have several C++ cores: **a2600** (Atari 2600), **lynx**, **tgbdual**,
**VB** (Virtual Boy), **GBA**, and now **c64**. Each of the older ones had
one of two defences:

- **a2600, lynx, tgbdual** *capture* the tables. Their overlay linker
  scripts have a rule that redirects `.ARM.extab.text.*` and
  `.ARM.exidx.text.*` into their own overlay's linker block. The tables
  still exist, but they live in the overlay, on the SD card, not in
  internal flash.
- **VB, GBA** *prevent* the tables. They compile with `-fno-exceptions
  -fno-unwind-tables -fno-asynchronous-unwind-tables`, so the tables are
  never generated. No tables, no leak.

C64 had **neither**. No capture rule, no `-fno-exceptions`. It was the only
C++ overlay core that let the compiler generate the tables and then let the
linker put them wherever the default said — which was the resident section.

## The fix

Three flags, one core's compile rule:

```makefile
-fno-exceptions -fno-unwind-tables -fno-asynchronous-unwind-tables
```

Added to C64's C++ compile rule only. Identical to what `Core/Src`'s own
C++ files already use, and what VB and GBA already use. Recovers **5.6 KB**
of internal flash. Changes no behavior — there is no `throw`/`catch` in
Frodo to remove. The full map-file audit traced 100% of the resident
`.ARM`/`.ARM.extab` content to `build/c64/*.o` plus those two libgcc
objects; zero remained after the flags went in.

The 32-byte overflow disappeared. The 44-byte headroom came back as a
5.6-kilobyte headroom. We re-listed the Ocean clock scene that an earlier
alarm fix had to delist to pay its 32 bytes (see
[the clock alarm devlog](/devlog/clock-alarm-the-one-you-couldnt-turn-off)).

## The lesson

Two things.

**A linker section is a default, not a destination.** If you don't tell the
linker where a section goes, it picks — and what it picks is "wherever
things like it already are." For `.ARM.extab`, that is the resident block.
For an overlay core, that is the wrong answer. Every section your core
emits — code, data, BSS, exception tables, init arrays, anything — needs
either an explicit destination in the overlay's linker rule, or a compiler
flag that stops it being generated. "It compiled and linked" is not the
same as "it linked correctly."

**C++ on a constrained device needs to be told it is on a constrained
device.** The language defaults assume a hosted environment with a runtime,
a stack unwinder, and an exception delivery path. The device has none of
those. `-fno-exceptions` is not a style choice on bare-metal Cortex-M; it
is the difference between shipping and not shipping. Every C++ core we have
that forgot the flag paid for it in flash they didn't have, for features
they didn't use.

The C64 runs now. Its tables are gone, not relocated — gone, because they
were never needed. And the launcher has its five and a half kilobytes back,
which is more than enough to fit the alarm fixes, the Ocean scene, and a
little headroom for whatever breaks next.
